# 初始 SRS 分析与范围界定（baseline-v1）

> 对应指导书 3.2 初始业务需求与附录 B。本文是编码前的需求分析成果，用于界定“做什么、不做什么、依据什么验收”。

## 1. 项目目标与边界

CampusEvent 面向校园活动场景，解决“管理员发布活动—学生报名—管理员审批—结果通知”的闭环。系统为单机 Web 应用（Flask + SQLite），使用固定演示账号，不做注册、密码、复杂权限。

**范围内**

- 活动的创建、编辑、删除、浏览、按名称搜索；
- 两类报名规则：直接报名、管理员审核；
- 报名、取消、审批、状态流转与名额约束；
- 站内消息 + 模拟邮件两类通知；
- 按活动统计已通过数、待审核数与剩余名额。

**范围外**

用户注册与密码体系、多租户、真实邮件/短信网关、消息队列、支付、签到、移动端 App、第三方日历同步。AI 不得以“更完整”为由自行加入上述功能。

## 2. 角色与权限

| 角色 | 演示账号 | 权限 |
| --- | --- | --- |
| 学生 Student | s1—s4 | 浏览/搜索活动、查看详情、报名、取消自己的报名、查看自己的报名与站内消息 |
| 管理员 Admin | admin | 创建/编辑/删除活动、审批报名、查看全部报名与通知台账 |

固定账号仅用于课程演示，登录不设密码；这不是可交付的真实身份认证方案，已在 README 的“已知限制”中声明。

## 3. 业务规则解读（附录 B.2）

| 规则 | 原文要点 | 本项目的落地方式 | 可验证用例 |
| --- | --- | --- | --- |
| R1 直接报名 | 名额充足且符合条件时创建“已通过”，并产生通知 | `DirectRegistrationPolicy` 判断剩余名额；通过后 `RegistrationService` 提交事务并发布 `RegistrationApproved` 事件 | C1、C2、C4 |
| R2 审核报名 | 提交后为“待审核”，管理员批准/拒绝 | `ReviewRegistrationPolicy` 固定返回 PENDING；`ApprovalService` 负责批准/拒绝 | C5、C6、C7 |
| R3 名额口径 | 只统计“已通过”，待审核不占名额；满员后不得批准 | `RegistrationStats.approved` 只统计 approved；批准时在 `BEGIN IMMEDIATE` 事务内再次计数 | C4、C8 |
| R4 重复报名 | 同一学生同一活动不得有两条“待审核/已通过”；取消或拒绝保留历史，可再次申请 | 部分唯一索引 `ux_registrations_active` + `find_active` 双重保护 | C3、规则测试 |
| R5 取消与时间窗 | 学生可取消待审核/已通过；活动开始后不允许新增报名 | 取消仅允许 active 状态；`Activity.is_open_for_registration(now)` 拦截开始后的报名 | C9、规则测试 |
| R6 通知失败 | 通知失败应留痕，不得让已合法提交的报名无声消失 | 报名先提交事务、后发布事件；订阅者异常被隔离并写入 `notification_deliveries` | 通知失败测试 |
| R7 持久化与删除 | 活动/报名持久化；删除有报名的活动需拒绝或软删除并说明 | 选择“拒绝删除并提示”，保留历史报名，避免级联丢失 | 删除保护测试 |

## 4. 领域对象识别

从需求文本中提取名词与动词，得到候选对象，再按职责归并：

| 候选 | 归类 | 职责 | 不承担的职责 |
| --- | --- | --- | --- |
| Activity | 实体 | 活动信息、容量、报名方式、是否可报名 | 不负责写报名记录 |
| Student | 实体 | 学生身份、邮箱、角色 | 不负责权限判断之外的业务 |
| Registration | 实体 | 一次报名的状态与历史 | 不负责决定自己能否被创建 |
| RegistrationPolicy | 策略接口 | 判断报名能否通过、通过后是什么状态 | 不写数据库、不发通知 |
| RegistrationService | 应用服务 | 编排校验、事务、事件发布 | 不渲染页面、不直接写消息 |
| ApprovalService | 应用服务 | 审批状态流转与容量复核 | 不处理报名创建 |
| NotificationService/订阅者 | 观察者 | 把领域事件翻译为站内消息/邮件 | 不修改报名状态 |
| EventBus | 基础设施 | 分发事件、隔离订阅者异常 | 不持有业务规则 |

职责边界的关键判断：

1. **Registration 是状态载体，不是规则载体**。把“能否报名”放进实体，会让实体依赖仓储与全局配置；因此规则放在策略，编排放在服务。
2. **RegistrationService 不直接写 messages 表**。报名与通知是两类变化原因，若写在一起，新增通知渠道就要改报名服务。
3. **统计是查询职责**，由 `RegistrationStats` 值对象与仓储聚合查询完成，不放进 Activity 实体（避免每次读活动都触发报名统计）。

## 6. 非功能需求

| 类别 | 要求 | 实现与证据 |
| --- | --- | --- |
| 可运行性 | 按 README 从零安装依赖并启动 | 项目 venv + `requirements.txt`，`run.py`；实测启动成功 |
| 可测试性 | 核心规则有自动化测试 | pytest 26 条，覆盖 C1—C10 与边界 |
| 数据一致性 | 并发报名不超员、不重复 | `BEGIN IMMEDIATE` 写事务 + 唯一索引 |
| 可观测性 | 通知失败可追溯 | `notification_deliveries` 记录渠道、状态、错误 |
| 可维护性 | 报名规则与通知渠道可扩展 | 策略模式 + 观察者模式；见设计模式决策报告 |
| 易用性 | 中文界面、明确错误提示、无堆栈泄漏 | 统一 flash + 领域异常翻译 + 403/404/500 页面 |
| 规模 | 百级活动/报名正常操作 | SQLite 索引 + 分页上限；演示数据 4 活动 |

## 7. 需求歧义与设计决策

| 歧义点 | 可选方案 | 决策与理由 |
| --- | --- | --- |
| 删除有报名的活动 | 级联删除 / 拒绝删除 / 软删除 | 基线选择**拒绝删除并提示**：历史报名是审计依据，级联删除会静默丢数据；软删除留到变更阶段作为 CR-02 的能力扩展 |
| 待审核是否占名额 | 占用 / 不占用 | **不占用**，与附录 B.2 第 3 条一致；批准时再次检查容量（C8） |
| 取消已开始活动的报名 | 允许 / 禁止 | 规则只禁止“新增报名”，因此**允许取消**；取消用于释放名额，不影响已发生事实 |
| 活动开始后能否审批 | 允许 / 禁止 | 需求未限制，**允许**；审批只校验状态与容量，避免加入未要求的规则 |
| 通知失败与事务 | 同事务 / 事务后 | **事务后**：报名已合法提交，不因通知失败回滚；失败写入台账并可查 |
| 通知重复 | 无防护 / 事件 ID 幂等 | **事件 ID + (event_id, subscriber, student_id) 唯一约束**，重复投递直接跳过 |

## 8. 验收依据

基线验收采用指导书 3.5 的 C1—C10；实现层另补充策略、边界、通知失败、权限与删除保护测试。每条用例均给出“操作—预期—实际—证据”，见《回归测试表》与 `tests/`。
