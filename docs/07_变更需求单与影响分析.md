# 需求变更单与影响分析（change-v2）

> 依据：教师发布的《实验二教师专用材料》中的 CR-01（新增年级限定报名）与 CR-02（新增邮件通知），以及指导书 3.6 的流程要求——初版验收并保存 `baseline-v1` 后，先提交影响分析，再基于 baseline 新建分支实现，最后统一回归。
>
> 本项目严格保留 `baseline-v1` 源代码不变；`change-v2` 是在其之上的一次增量变更。本文件第 1—4 节写于实现前，第 5—8 节回填实际改动与验证结果，不以实现结果反推分析。

## 1. 变更单 CR-01：新增年级限定报名

### 1.1 变更背景与要求

学校新增仅面向大二、大三学生的活动类别：

1. Activity 支持“年级限定直接报名”规则；
2. Student 新增 `grade` 字段，取值 1—4；
3. 仅 `grade ∈ {2,3}` 的学生可以报名此类活动，其他年级收到明确提示；
4. 该规则同时遵守名额限制、活动开始时间、重复报名等公共约束；
5. 原有“直接报名”和“审核报名”行为不得改变；
6. 期望设计：可通过新增独立策略或可组合规则实现，但应解释设计选择，尽量不修改 `RegistrationService` 核心流程。

### 1.2 变更理由

年级限定是比“直接/审核”更细的准入规则：它不改变报名后的状态流转（仍是立即通过），只是在判定前增加一个业务前置条件。这正是检验策略模式“变化点是否被隔离”的合适变更。

### 1.3 影响分析（实现前）

| 影响对象 | 变更内容 | 风险 |
| --- | --- | --- |
| `Student` | 增加 `grade: int`（1—4） | 既有数据无年级；需迁移赋默认值并保住演示账号语义 |
| `students` 表 | 增加 grade 列 + CHECK | SQLite 需 ALTER TABLE；默认值要合法 |
| `PolicyType` 枚举 | 增加 `GRADE_LIMITED` | 数据库 CHECK、表单下拉、页面标签同步 |
| `RegistrationPolicy` | 新增 `GradeLimitedRegistrationPolicy` | 不能重复实现容量逻辑；公共规则不能被绕过 |
| `PolicyRegistry` | 注册第三个策略并保持顺序 | 下拉展示顺序 |
| `ActivityService` 校验 | 接受新 `policy_type` | 无效值仍应报错 |
| 页面 | 活动详情提示、报名按钮文案、拒绝提示 | 普通活动页面不能回归 |
| 演示数据 | 学生年级、年级限定示例活动 | 既有数据库不会自动补活动 |
| 测试 | CR1-01—04 + 容量/重复/原策略回归 | 需要能切换年级账号 |

**预计修改范围**：领域模型、策略、仓储映射、迁移、种子与页面；`RegistrationService.register()` 不应出现新的类型分支。**预计新增测试**：6—8 条。

## 2. 变更单 CR-02：新增邮件通知

### 2.1 变更背景与要求

管理员希望在站内消息之外，同步向报名学生发送邮件通知：

1. 不接入真实邮件服务器，由教师/学生提供的 **MockEmailSender** 模拟发送；
2. 记录收件人、主题、内容、状态与时间；
3. 对“报名通过、审核通过或拒绝”的事件，原有站内通知继续运行，同时新增模拟邮件；
4. 邮件发送故障必须记录错误，但不得错误回滚已成功提交的报名；
5. 避免同一业务事件被重复发送两次；
6. 期望设计：使用观察者模式或事件通知结构新增邮件订阅者/处理器，不把邮件发送代码写入 `RegistrationService`。

### 2.2 现状说明与本次口径

初版（baseline-v1）的 P2-F07 已包含“站内消息 + 模拟邮件出件箱”，即 `email_outbox` 表与 `EmailNotificationSubscriber`。但初版：

- 没有独立的邮件发送记录（收件人、主题、内容、**状态**、**时间**分散在出件箱与投递台账）；
- 邮件发送逻辑是 `OutboxEmailGateway`，没有教师要求的 `MockEmailSender` 抽象；
- 邮件级幂等依赖订阅者层，缺少 `(event_id, student_id)` 的邮件台账唯一约束。

因此本次 CR-02 的口径是：**保留并复用既有观察者结构，把邮件通道正式化为 MockEmailSender，新增 `email_deliveries` 邮件台账，补齐失败记录与邮件级防重，并用测试证明“站内通知继续运行、失败不回滚、不重复发送”。** 这不是重复造一个邮件渠道，而是按变更单把已有能力补到可验收的形态。

### 2.3 影响分析（实现前）

| 影响对象 | 变更内容 | 风险 |
| --- | --- | --- |
| `NotificationContent` | 增加 `event_id`，供邮件幂等使用 | 文案构建器四个分支都要填 |
| `EmailNotificationSubscriber` | 改为调用 `MockEmailSender` | 订阅者模板与站内订阅者不应改动 |
| 新增 `MockEmailSender` | 发送落库、失败抛错、重复跳过 | 失败必须发生在业务事务之外 |
| 新增 `email_deliveries` 表 | 收件人/主题/内容/状态/错误/时间/传输编号 | 唯一约束 (event_id, student_id) |
| `EmailDeliveryRepository` | record / find_for_event / list_recent | 与 `email_outbox` 的职责区分 |
| 容器与配置 | 装配 MockEmailSender，支持故障注入 | `EMAIL_GATEWAY=failing` 兼容既有测试 |
| 管理端通知台账 | 展示邮件发送记录与失败原因 | 页面不报错、字段完整 |
| 测试 | CR2-01—04 + 迁移 + 重复事件 | 与既有 `test_notifications.py` 不冲突 |

**预计修改范围**：通知服务、仓储、容器、迁移、管理页；**`RegistrationService`、`ApprovalService` 不应修改**，`InSiteNotificationSubscriber` 不应修改。**预计新增测试**：5—7 条。

## 3. 设计选择

### 3.1 CR-01：继承直接报名策略，而不是重写一套

备选：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 继承 `DirectRegistrationPolicy`，只增加年级判定 | 复用容量逻辑；公共规则不变；新增类最小 | 继承层级多一层 | **采用** |
| 直接继承 `RegistrationPolicy`，重写年级+容量 | 层级扁平 | 容量规则重复；两处易不一致 | 否 |
| 可组合规则（年级规则 + 直接规则链） | 理论上最灵活 | 需要引入规则组合框架，超出本次变更范围 | 否（记录为未来演进） |

### 3.2 CR-02：MockEmailSender 放在观察者订阅者侧

- 业务服务只发布“已发生事实”，不知道有几个渠道；
- 邮件发送器只负责“把一封邮件记下来/模拟失败”，不查报名、不改状态；
- 失败由订阅者隔离并写投递台账，`MockEmailSender` 另写邮件台账；
- 幂等由订阅者 claim + 邮件台账唯一约束双重保证。

## 4. 实施顺序（实际执行）

## 6. 迁移方案（v1 → v2）

1. `PRAGMA foreign_keys = OFF`，开启显式事务；
2. `ALTER TABLE students ADD COLUMN grade INTEGER NOT NULL DEFAULT 1 CHECK (grade BETWEEN 1 AND 4)`；
3. 演示账号按原有语义赋年级：s1 大二、s2 大三、s3 大一、s4 大四、admin 大四；其他学生默认大一；
4. 重建 `activities`：`policy_type` CHECK 扩展为 `('direct','review','grade_limited')`，复制全部旧数据；
5. 新建 `email_deliveries`：收件人、主题、正文、状态、错误、发送时间、传输编号，唯一约束 `(event_id, student_id)`；
6. 版本号写为 2；任何异常整体回滚。

由 `test_cr2_05_migration_from_v1_preserves_data` 验证：旧活动/报名保留，s1 年级迁移为大二，`grade_limited` 可写入，非法年级被 CHECK 拒绝，邮件台账唯一约束生效。

## 7. 风险与应对（实现后闭环）

| 风险 | 应对 | 实际结果 |
| --- | --- | --- |
| 既有学生没有年级，迁移后无法报名 | 增加列时给合法默认值，并按演示账号语义回填 | 已闭环：C18 类迁移测试验证 s1=大二、旧报名保留 |
| SQLite 无法修改 activities 的 CHECK | 重建表 + 复制数据 + 重命名，全程事务 | 已闭环：`_upgrade_v1_to_v2`，旧活动数不变 |
| 年级判断重复实现容量逻辑 | 继承 Direct，只覆写年级判断后调用父类 | 已闭环：`GradeLimitedPolicy` 仅 6 行判定 |
| 年级提示不明确 | 拒绝原因带“仅限大二、大三”和实际年级 | 已闭环：CR1-03/04 断言提示含“大一”“大四” |
| 邮件失败导致报名回滚 | 发送在事务提交后由订阅者执行，失败只记录 | 已闭环：CR2-03 报名仍 approved，邮件记录 failed |
| 重复事件产生多封邮件 | 订阅者 claim + `(event_id, student_id)` 唯一 | 已闭环：CR2-04 只增加 1 封 |
| 旧邮件网关删除影响既有测试 | `EMAIL_GATEWAY=failing` 兼容，故障文案保留 SMTP | 已闭环：原 `test_notifications.py` 3 条全过 |
| 管理页字段缺失 | 传入 email_deliveries 并在模板展示 | 已闭环：页面截图与 200 响应验证 |

## 9. 结论

两项变更都验证了初版的设计假设：

- **CR-01**：第三种报名方式只新增 1 个策略类 + 注册 1 行，`RegistrationService` 零改动；年级判断被隔离在策略层，公共约束仍由模板方法统一执行。
- **CR-02**：邮件发送被放在观察者订阅者侧，站内订阅者与业务服务无需修改；`MockEmailSender` 把“收件人/主题/内容/状态/时间”落成独立台账，失败只留痕、不回滚，重复事件不重复发送。
- 真正需要人工保证的不是“用了模式”，而是**迁移的兼容性、失败边界与幂等约束**；这些由迁移测试、故障注入测试与唯一约束固定下来。
