# 设计模式决策报告（baseline-v1）

> 本报告回答三个问题：为什么使用策略/观察者、增加了什么成本、未来怎样扩展。结论均以代码与测试为依据，而不是以“用了模式”本身作为正确性证明。

## 1. 设计目标与约束

| 目标 | 来源 | 衡量方式 |
| --- | --- | --- |
| 报名规则可替换、可扩展 | B.3：至少一个策略接口与两种实现 | 新增报名方式需要改动的核心类数量 |
| 报名与通知解耦 | B.3：观察者或等价事件机制 | 新增通知渠道需要改动的文件数 |
| 名额、重复、状态边界正确 | B.2 业务规则 | C3、C4、C8 等验收用例 |
| 通知失败可追溯且不影响报名 | B.2 第 6 条 | 故障注入测试 + 台账记录 |
| 结构可讲解、可维护 | 课程目标 LO2 | 类图、依赖方向、SOLID 对照 |

## 2. 决策一：用策略模式表达报名规则

### 2.1 问题

报名规则包含稳定部分（活动必须未开始、不能重复有效报名）与变化部分（满员时拒绝还是进入待审核，报名后是什么状态）。如果写成：

```python
if activity.policy_type == "direct":
    ...
elif activity.policy_type == "review":
    ...
```

每新增一种报名方式都要修改 `RegistrationService`，并重复公共校验；分支还会与页面、文案、统计耦合。

### 2.2 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 服务内 if/elif | 代码最少 | 违反 OCP；公共规则重复；测试需覆盖所有分支组合 | 否 |
| 为活动建子类（DirectActivity、ReviewActivity） | 面向对象 | 活动类型与报名规则耦合；活动还要承担持久化字段；规则变化要改实体 | 否 |
| 规则引擎/配置表 | 非程序员可改 | 引入表达式解析与调试成本；课程范围外 | 否 |
| 策略接口 + 注册表 + 模板方法 | 变化点隔离、公共规则只写一次、可单测 | 类数量增加、调用链变长 | **采用** |

### 2.3 结构

- `RegistrationPolicy.evaluate(ctx)`：模板方法，固定执行顺序；子类不能绕过公共规则。
- `decide(ctx)`：唯一变化点，返回 `PolicyDecision(allowed, target_status, reason)`。
- `PolicyRegistry`：把“选择哪个策略”从服务中移出；服务只依赖注册表。
- `RegistrationContext`：一次判定的完整输入，策略无需回查数据库，便于构造边界测试。

### 2.4 名额检查放在哪里

指导书要求说明“名额检查属于公共规则还是策略责任”。本项目的答案是**拆成两半**：

- **名额口径是公共规则**：只有 `APPROVED` 占用名额；`remaining = capacity - approved` 由上下文统一计算，两个策略共享同一口径，不会出现“直接报名算待审核、审核报名不算”的不一致。
- **满员后的行为是策略责任**：直接报名必须拒绝；审核报名允许进入待审核（待审核不占名额）；若未来新增候补规则，则进入候补队列。三者对“满员”做出不同业务决策，这正是变化点。

因此公共模板方法只校验“活动开始时间、重复有效报名”，不把“是否为满员即拒绝”写死。这样 C4（直接报名满员拒绝）与 C5（审核满员仍可提交）可以同时成立。

### 2.5 代价

- 多 3 个类（接口、两个实现）+ 1 个注册表 + 2 个值对象；初次阅读需要沿调用链跳转。
- 策略只能拿到 `RegistrationContext` 提供的数据，若未来规则需要“学生信用分”等新信息，需要扩展上下文，而不是在策略里直接查库（这是有意的约束，避免策略变成“上帝类”）。

### 2.6 扩展方式

新增报名方式（如候补）：实现 `RegistrationPolicy`，在 `PolicyRegistry` 注册，活动表单增加选项，补充策略单测与端到端用例。`RegistrationService`、`ApprovalService` 的报名主流程不需要修改；这一扩展路径可在后续需求变更中验证。

## 3. 决策二：用观察者/事件总线解耦通知

### 3.1 问题

报名成功后需要写站内消息，可能还要发邮件；如果 `RegistrationService` 直接写 `messages` 表并调用邮件网关：

- 报名服务同时承担业务规则、消息文案、渠道重试，职责膨胀；
- 新增渠道要改报名/审批服务；
- 通知失败可能与报名事务纠缠，导致“通知失败→报名回滚”。

### 3.2 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 服务内直接写消息 | 直观、少类 | 报名与通知耦合；新增渠道改核心服务 | 否 |
| 消息队列（RabbitMQ/Kafka） | 削峰、可靠投递 | 超出实验边界，需要额外运维 | 否（明确不引入） |
| 框架信号（Flask signals） | 轻量 | 隐式全局订阅、测试隔离差；事件与业务同进程但语义弱 | 否 |
| 领域事件 + 进程内 EventBus + 订阅者 | 解耦、可测试、可观测、无需中间件 | 投递为同步、无重试队列；需要自建幂等台账 | **采用** |

### 3.3 结构

- 事件是“已发生事实”的不可变快照，携带 `Activity`、`Student`、`Registration`，订阅者不必回查数据库。
- `EventBus.publish` 逐个调用订阅者，单个订阅者异常被捕获并记录，不影响其他订阅者，也不影响已提交的业务事务。
- 订阅者模板负责幂等 claim、逐人投递、成功/失败落账；渠道只实现 `deliver`。
- 文案集中在 `NotificationContentBuilder`，新增渠道不需要复制文案。

### 3.4 通知失败与重复通知

- **失败**：`EmailGateway` 故障注入测试证明：邮件抛错时，报名仍为 approved，站内消息仍送达，邮件投递记录为 failed 并保存错误。
- **重复**：`notification_deliveries` 的唯一约束 `(event_id, subscriber, student_id)`；同一事件重复 publish 时第二次 claim 返回 None，直接跳过。
- **事务边界**：报名事务提交后才 publish；因此通知失败不能回滚报名，符合 B.2 第 6 条。

### 3.5 代价

- 通知是同步投递，邮件网关慢会拖慢请求；真实系统需要异步队列，本实验在 README 中声明限制。
- 事件与订阅者之间没有编译期约束，新增事件类型要同步扩展 `NotificationContentBuilder`；已用类型判断集中处理。
- 多一张投递台账表与一套 claim/mark 逻辑。

## 4. 决策三：删除有报名的活动

| 方案 | 后果 | 选择 |
| --- | --- | --- |
| 级联删除报名 | 历史与统计丢失，误删不可恢复 | 否 |
| 软删除（加 deleted 标记） | 保留数据，但所有查询、容量、唯一索引都要加过滤条件；基线需求未要求 | 暂不 |
| 拒绝删除并提示 | 简单、数据安全，管理员可先处理报名 | **基线采用** |

变更阶段若需要下架活动，可在不删除历史的前提下扩展“软取消”能力；基线不做该功能，避免超出初始需求范围。

## 5. 决策四：数据访问与事务

- 不使用 ORM：SQLite 标准库足够，SQL 明确、便于讲解索引与事务；代价是手写映射代码。
- 仓储只做对象↔行转换，业务判断不进入 SQL。
- 写操作统一 `BEGIN IMMEDIATE`：SQLite 单写者模型下，先取写锁再检查容量，避免“检查后写入前被抢占”的竞态；读操作 autocommit。
- 迁移以版本号管理，变更阶段通过新增迁移步骤升级，不删库重建。

## 6. 收益与成本对照

| 维度 | 不使用模式 | 使用策略 + 观察者 |
| --- | --- | --- |
| 新增一种报名方式 | 改服务分支、页面、测试，易漏公共规则 | 新增策略类 + 注册，主流程不变 |
| 新增一种通知渠道 | 改报名/审批服务，复制文案 | 新增订阅者 + 装配一行 |
| 单元测试 | 需构造完整服务与数据库 | 策略可直接用上下文测试；订阅者可用假网关测试 |
| 代码量 | 更少 | 基线约 2.5k 行源码、25 个 Python 文件（含注释与类型注解） |
| 调试成本 | 调用链短 | 一次报名跨 6 个协作对象，需要看事件与投递台账 |
| 适用性 | 规则固定的小系统 | 规则/渠道预期变化、需要可解释设计的系统 |

**可测指标**（基线记录，变更后对照见《09_可维护性对照.md》）：

- 核心业务类：`RegistrationService`、`ApprovalService`、`ActivityService` 共 3 个；
- 策略实现：2 个；通知订阅者：2 个；
- 报名主流程分支：`RegistrationService.register` 中无 `policy_type` 判断（0 处）；
- 通知渠道判断：`NotificationContentBuilder` 之外无渠道分支（0 处）；
- 测试：26 条，全部通过。

## 7. 结论与局限

策略模式解决了“报名规则变化”，观察者解决了“通知渠道变化”，两者都把变化点收敛到可独立测试的类中；但模式不是目的：

- 若报名规则永远只有两种且不再变化，if/elif 更划算；
- 当前实现的通知是同步、无重试，投递失败只留痕不补偿；
- 事件与订阅者的契约靠类型与测试保证，没有 schema 版本管理。

这些局限将在实验报告中作为“尚存问题”如实说明。
